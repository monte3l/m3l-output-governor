## Closed

| # | Item | Result |

| 1 | Whether transcripts record thinking tokens separately | **Yes.** Assistant rows carry `usage.output_tokens_details.thinking_tokens` (checked 2026-10-19). The docs' statusline, OpenTelemetry and mod `usage` fields fold thinking into output, so the transcript is the only exact source found |
| 2 | Whether a tool-result hook layer is worth building | **No, on this history.** 359 sessions and 12,969 requests under the monte3l workspace: Bash results of 8,000 characters or more were 181 of 7,731 and carry about 2% of billed input by the re-read estimate (5% at a 4,000 gate, 8.5% at 2,000, 10.4% at 1,000). The plan's bar was 10% at the planned gate. The estimate ignores compaction and counts cache reads at full weight, so it overstates. Thinking was 36% of output tokens |
| 3 | Whether Claude Code caps Bash output | **Yes, and it is documented** (`tools-reference#output-limits`, `env-vars`, `settings-reference#bashoutputmaxchars`). A successful command's output is inline up to about 30,000 characters by default (`bashOutputMaxChars`, clamped to 4,000 to 128,000, v2.1.261 or newer); past that Claude gets a file path and a preview of up to 2,000 characters. A failed command gets a head-and-tail excerpt of about 10,000 characters with no path. Matches the data: the largest stored result was 28,486 characters, and the five truncated results were each 5,000 + marker + 5,000 characters. The cap is why large Bash results are already a small share of input |

Because closed items 4 and 5 show a hook's replacement is what is stored and
re-read, `session.append` would add nothing for tool results over a command hook.
Closed items 8 and 9 add a reason to prefer the command hook if one is ever
built: its replacement is visible on screen, so the user can see what Claude saw,
while a `session.append` rewrite changes only what Claude sees.

## Not verifiable

- The re-read estimate is a model, not a measurement: it ignores compaction and prices a cache read like fresh input.
- The measurement covers one user's sessions. A different workload, for example heavy test-runner use that stays under the 30,000 cap, could clear the 10% bar; rerun `scripts/measure.mjs` on it before reopening a hook layer.
- Probes used Claude Haiku 5.5 and one run each, so they show what is possible, not how often.
- The literal truncation marker, the `<persisted-output>` wrapper and the 5,000 + 5,000 split are observed in transcripts and one live repro, not documented. The docs pages `env-vars` and `settings-reference` were not read to the end, so a mention there is not ruled out. The source of truth would be the Claude Code source or an issue at github.com/anthropics/claude-code.
